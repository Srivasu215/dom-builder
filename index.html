Separating UI structure from the code that builds it. Describe what to render with data; let the engine compile and mount native HTML elements with zero virtual DOM overhead.

The 2 Foundation Pillars

Two Specialized Engines, One Ecosystem

Clean separation between the high-level business component orchestrator and the low-level universal DOM tag compiler.

Pillar 01 • High-Level Runtime 🖥️

json-renderers

The Component Orchestrator. Accepts raw business data, columns (the story about the data), and type (the component intent). Coordinates contract validation, headless spec compilation, and DOM placement.

What It Delivers:
  • Composite Tables: Automated # serials, numeric alignment, and footer totals in <tfoot>.
  • Autocomplete Datalists: Native HTML5 <datalist> without external JS widgets.
  • Select Dropdowns & Forms: Declarative options binding and schema controls.
  • The House-Building Story: Conceptual mental model in subDoc/.

Pillar 02 • Low-Level Compiler ⚙️

json-to-tag

The Universal DOM Compiler. A zero-dependency engine that transforms declarative JSON specifications into real native HTML DOM elements via recursive specification traversal.

What It Delivers:
  • Recursive Traversal: Visits nested parent-child trees handling objects, arrays, and text.
  • Zero Virtual DOM: Direct synthesis via native document.createElement().
  • HTML Tag Catalog: Comprehensive JSON catalog of supported HTML5 tags.
  • Independent Utility: Can be used standalone in any project without renderers.

Working Principle

How dom-builder, json-renderers and json-to-tag Work Together

These repositories have different responsibilities. The overview below describes the roles shown in this documentation; exact behavior depends on the configuration and APIs used by the project.

01 · Platform / Overview

dom-builder

The umbrella project and documentation entry point. It explains how declarative JSON can describe a UI and how the rendering/compiler pieces fit together.

Open dom-builder repository ↗
02 · Component Runtime

json-renderers

Accepts a higher-level render request, such as a component type, data, columns and a target element ID. It coordinates the component-specific rendering workflow and can place the resulting UI in the requested target.

Open json-renderers repository ↗
03 · DOM Compiler

json-to-tag

Takes a JSON description of tags and their properties/children, walks the nested structure, creates native HTML elements, applies supported attributes and content, and assembles the DOM tree.

Open json-to-tag repository ↗

Example workflow

1. Request
Component type + data + columns + target ID
2. json-renderers
Coordinates the requested component workflow
3. JSON tag spec
Describes elements, attributes and children
4. DOM output
json-to-tag builds elements; output is mounted at the target

Important distinction: json-renderers is the higher-level component workflow, while json-to-tag is the lower-level JSON-to-native-DOM compiler. The dom-builder repository presents the overall idea and connects the documentation. The exact internal hand-off can vary by implementation; check the source code for a specific call path.

What happens inside json-renderers?

  1. The caller supplies a render request with the intended component type and its data/configuration.
  2. The runtime selects the component-specific path and prepares the specification needed for that UI.
  3. The target element ID identifies where the rendered output should appear.
  4. The UI is created and connected to the target through the rendering workflow.

What happens inside json-to-tag?

  1. Read the JSON node and identify its tag, properties, attributes and child content.
  2. Create the corresponding native element with browser DOM APIs.
  3. Process nested children recursively, preserving their parent-child relationship.
  4. Return/assemble the element tree so the caller can attach it to a page container.
